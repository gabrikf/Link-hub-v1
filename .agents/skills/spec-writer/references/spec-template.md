# Spec Template

This file defines the exact structure of the artefacts generated by `#spec-writer`.

---

## Directory Structure

```
docs/specs/[feature-name]/
├── SPEC.md              # Main spec
├── definitions.md       # Feature dictionary (see SKILL.md §4.6)
├── contracts/           # Executable zod schemas + real fixtures (see SKILL.md §4.5)
│   ├── README.md        # Provenance/status of each contract
│   ├── <endpoint>.schema.ts
│   └── fixtures/<endpoint>.example.json   # 3 cases: full (REAL capture), empty, missing-field
├── variants.md          # Variant/mode matrix — MANDATORY if the feature renders a discriminated set (SKILL.md §4.7)
├── tasks.md             # Atomic implementation tasks
├── harness.md           # Verification harness
├── decisions.md         # Decision record (lightweight ADR)
├── refs/                # The dev's original inputs — preserved, never generated
│   ├── po-specs/  design/  api/
└── design/              # Visual references
    ├── README.md        # How to read the designs
    └── *.html|*.png     # Supplied design files
```

## 6. Architecture and Data

### 6.1 Planned file structure
```

apps/web/src/features/[feature-name]/
├── pages/
│ └── [page-name].tsx
├── components/
│ └── [component].tsx
├── hooks/

└── lib/
└── [helper].ts

# If the feature touches the API:

├── [name].use-case.ts
└── [name].use-case.test.ts
apps/api/src/infra/http/controllers/[module]/...
apps/api/src/infra/di/container.ts # MODIFY — register the new use case

# Contract:

packages/schemas/src/[module]/index.ts # extend, or add if genuinely new

```

### 6.2 API Contracts

Contracts are **executable** and live in `contracts/*.schema.ts` (zod schemas + fixtures).
This is only the index — never duplicate a schema as prose:

| Endpoint | Registration probed | Schema | Provenance | Status | G0 |
|----------|--------------------|--------|-----------|--------|----|
| GET /[resource] | bare \| /api/v1 \| both | `contracts/get-[resource].schema.ts` | API/Swagger \| INFERRED | validated \| PENDING | passed \| BLOCKING \| n/a |

**Rules:** a field that may be absent → explicit `.nullable()` (never a silent `.optional()`);
types always via `z.infer` (never a parallel hand-written interface); a fixture with 3 cases in
`contracts/fixtures/`, whose "full" case is a **real captured payload**; the schema is written
to be promoted into `packages/schemas/src/<module>/`, extending an existing module wherever one
exists.

### 6.3 State and Data Flow

```

User action → feature hook → TanStack Query → API (localhost:3333) → zod parse → cache → render

````

## 9. Dependencies

### API

- [ ] `GET /[resource]` — status: [live (G0 passed) | live but G0 BLOCKING | not built (mock)]
- [ ] `POST /[resource]` — status: [...]

> **If the endpoint is not live:** infer the contract, mark `Status: PENDING API validation`,
> and drive the hook from a local mock (an MSW handler or a typed stub in the feature's `lib/`
> — check what neighbouring features already do before adding a new mocking mechanism).
> Infer the contract from the requirements, the design, and the nearest existing
> `packages/schemas` module.

### Inferred-contract flow

1. **Infer** the schema from requirements + design + the closest existing schema module
2. **Generate** `contracts/<endpoint>.schema.ts` with
   `Provenance: INFERRED | Status: PENDING API validation`
3. **Create** an explicit API-validation task in `tasks.md`
4. **Drive** the query/mutation hook from the mock (mock data = the "full" fixture)
5. When the route ships → run the **G0 probe**, capture the real payload, flip to
   `Status: validated`, replace the mock, and re-run the contract sensor

### Frontend

- [ ] Shared component X — already exists
- [ ] Shared component Y — must be created; used by [N] places, so it goes in `shared-components/`

### Infrastructure

- [ ] Docker Postgres needed to test? (`bash db-manage.sh start`)
- [ ] Funded `OPENAI_API_KEY` needed? (search/embedding suites)
- [ ] Database migration required?

## 10. Risks and Mitigations

| Risk                         | Impact     | Mitigation                                             |
| ---------------------------- | ---------- | ------------------------------------------------------ |
| Endpoint not live            | UI blocked | Inferred contract + mock + G0 probe when it ships      |
| Design supplied as text only | Misread UI | Recorded as a risk; visual gate per delivery           |
| Contract changes mid-flight  | Rework     | Delta table in `refs/api/`, re-run the contract sensor |

## tasks.md — Template

```markdown
# Tasks — [Feature Name]

> **Total:** N tasks
> **Strategy:** [sequential | parallel-worktrees]
> **Estimate:** [time]
> **Spec:** [link to SPEC.md]

---

## Execution Order

Tasks are ordered by **dependency** — each depends only on those before it.

### Group 0: Gate (BLOCKING — nothing else starts until this passes)

#### Task G0: Endpoint liveness probe
- **Scope:** prove every endpoint claimed to exist actually answers real JSON
- **Applies to:** [list the endpoints with `Status: validated` or a supplied route]
- **Not applicable to:** [endpoints with INFERRED contracts — those follow the mock flow]
- **Procedure:**
  1. `bash db-manage.sh start` (if the endpoint needs Postgres), then `npm run dev:api`
  2. `curl -sS -o /dev/null -w '%{http_code}\n' http://localhost:3333/health`
  3. `curl -sS http://localhost:3333/docs/json | jq -r '.paths | keys[]' | grep -i '<resource>'`
  4. Probe **both** registrations — bare and `/api/v1` — with `Accept: application/json`,
     and record which one the web app will call
  5. Demand: 2xx **and** `content-type: application/json` **and** a body that parses as JSON
     **and** a body the schema in `contracts/` accepts
  6. Freeze the captured payload into `contracts/fixtures/<endpoint>.example.json`
- **Done when:** every listed endpoint passed all four demands and its real payload is frozen
- **If it fails:** **BLOCK.** Do not start any dependent UI task. Either the route is not live
  (→ switch that contract to INFERRED + mock + validation task) or it is registered on the
  other path (→ correct the spec). Report which, and why.
- **Depends on:** nothing

### Group 1: Foundation

#### Task 1: Contract
- **Scope:** the zod schema and its types
- **Files:**
  - MODIFY: `packages/schemas/src/[module]/index.ts` (extend the existing module)
  - or CREATE: `packages/schemas/src/[module]/index.ts` + export from `src/index.ts`
  - CREATE: the contract test that `.parse()`s the REAL captured fixture
- **Done when:** `npm run build:schemas && npm run check-types` passes and the contract test
  parses the real payload
- **Depends on:** G0

#### Task 2: Query hook
- **Scope:** the TanStack Query hook(s)
- **Files:**
  - CREATE: `apps/web/src/features/[feature]/hooks/use-[resource].ts`
- **Done when:** hook exported, fully typed off `z.infer`, response parsed, error path handled
- **Depends on:** Task 1

### Group 2: UI

#### Task 3: Page + route
- **Scope:** the page component and its route registration
- **Files:**
  - CREATE: `apps/web/src/features/[feature]/pages/[page].tsx`
  - MODIFY: `apps/web/src/router.tsx` (add the route by hand — routing is code-based)
- **Done when:** the screen renders all four states; the route is reachable at
  `http://localhost:5173/[path]`
- **Visual gate:** `node scripts/visual/run.mjs scripts/visual/scenarios/[feature].scenario.mjs`
  green before Group 3 starts
- **Depends on:** Tasks 1, 2

#### Task 4: Subcomponents
- **Scope:** the feature's internal components
- **Files:** CREATE: `apps/web/src/features/[feature]/components/[component].tsx`
- **Done when:** renders from the **parsed real fixture**, every variant row of `variants.md`
  covered
- **Depends on:** Task 3

### Group 3: Interaction

#### Task 5: Form and validation
- **Scope:** react-hook-form + zod
- **Files:** MODIFY/CREATE: `apps/web/src/features/[feature]/components/[form].tsx`
- **Done when:** submit works, validation shows inline errors, and **every required field in
  the table below has a mounted input in every mode where it applies**

**Field table (MANDATORY for any task that builds a form):**

| Field | Schema key | Payload path | Required? | Tab/mode where it renders |
|-------|-----------|--------------|-----------|---------------------------|
| Title | `title` | `block.title` | yes | pc, mobile |
| Provider | `provider` | `block.config.provider` | yes (kind=video) | pc |
| Layout | `layout` | `block.config.layout` | no | pc |

This table is generated from the zod schema, not from prose. A required field missing from
this table is a **dead Save button** waiting to happen: the form can never validate, and no
amount of clicking tells you which field is missing. The schema ⟷ UI sensor asserts this
table row by row, per mode.

- **Depends on:** Task 4

#### Task 6: Tests
- **Scope:** unit tests for the business rules and hooks; the variant matrix; the blank-screen
  sensor; the write-landed check for mutations
- **Files:** CREATE: colocated `*.test.ts(x)` beside what they test
- **Done when:** `npx vitest related <files> --run` green; `npm run test:coverage` no package
  below its floor
- **Depends on:** Tasks 2-5

---

## Per-Task Metadata

| Task | Files | Conflict risk | Parallelisable with |
|------|----------|-------------------|-------------------|
| G0 | none (probe only) | none | — (blocking root) |
| 1 | `packages/schemas` | **High** — consumed by api, web, mcp, extractor, training | — |
| 2 | feature hooks | Low | — |
| 3 | page + `router.tsx` | Medium (`router.tsx` is shared) | — |
| 4 | components | Low | Tasks 5-6 |
| 5 | form components | Low | Task 6 |
| 6 | tests | Low | Task 5 |
````

## design/README.md — Template

```markdown
# Design — [Feature Name]

## Source

- **Tool:** Figma (MCP) / Claude / Figma Make / screenshot / text description
- **Date:** [YYYY-MM-DD]
- **Fidelity:** [full design / screenshot only / text only — text only is a RISK, see SPEC.md §10]

## Files

| File              | Description               | State/Screen |
| ----------------- | ------------------------- | ------------ |
| `main-view.html`  | Main screen with the list | Filled       |
| `empty-state.png` | Empty state               | Empty        |
| `form-modal.html` | Create modal              | Clean form   |

## How to Read These

- The design is the **pixel-perfect reference** for the new feature only — the app shell
  around it already exists and must not be touched
- Use **Tailwind 4** for spacing, colour and typography
- Use `shared-components/` primitives and the Radix components already in use wherever they exist
- **Colours** map to the `DESIGN.md` violet/zinc language and the `SURFACE*` constants in
  `apps/web/src/shared-components/surface.ts` — **never a hardcoded hex**
- **Surfaces** come from `SURFACE`, `SURFACE_PROFILE`, `SURFACE_GLASS`, `SURFACE_INSET`,
  `SURFACE_EMPTY`. Padding stays at the call site; only the material is in the constant.
  Inventing a one-off surface string is how those constants came to exist in the first place.
- **Focus rings** and button hierarchy follow `DESIGN.md`, not the design file's approximation
- **Dark mode** is real: every surface constant carries its `dark:` variant. Check both.
- The design will not draw the error, empty or loading states. The spec defines them anyway.
```
