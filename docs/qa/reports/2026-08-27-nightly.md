## Session Debriefs

The loop's per-iteration debriefs live in `.nightly/MEMORY.md` (7 719 lines,
append-only, one section per iteration). What follows is the distillation.

### The disclosure lane (Atlas) — the most productive lane of the night

- **Ran:** iterations 3–29 and 101–116
- **Findings:** 7 bugs, 2 of them blockers. The pattern behind almost all of
  them: **the write path and the read path disagreed about what "blocked" means.**
  The denylist held a literal employer string; the agent published a *derived*
  form of it — a URL slug, an underscore join, a tech-stack entry, a cross-role
  attribution — and the literal comparison missed.
- **Edge cases attempted and clean:** hyphen slugs after the first fix,
  case variants, tags on the write path, `pending_review` posts staying private
  to anonymous readers.
- **Bugs filed:** `BUG-20260822-disclosure-external-url`,
  `BUG-20260822-disclosure-cross-role`, `BUG-20260822-disclosure-url-slug-variant`,
  `BUG-20260822-agent-self-publish`, `BUG-20260827-disclosure-underscore-slug`,
  `BUG-20260827-mcp-overstates-redaction`,
  `BUG-20260827-work-context-stack-unredacted`
- **Surprises:** `get_work_context` — the tool CraftHub calls the *only sanctioned
  source of employment detail* — was actively telling agents the payload was
  "already redacted" for six categories the api never redacted, and was handing
  over unredacted `role.stack` entries that the write path would then 400 on.
  The agent was being lied to by its own contract.
- **Suggested next charter:** a corpus of real `externalUrl` values to measure
  false-positive tolerance against (see `ESC-20260827-disclosure-slash-gap`).

### The four-state lane (Diego) — error states that lied

- **Ran:** iterations 33–49, 68–78
- **Findings:** two screens rendered **fabricated data** on a failed GET rather
  than an error. The layout editor drew a default arrangement with a live
  toolbar and "Changes save automatically"; the dashboard profile panel drew the
  empty state verbatim with a working Edit button. Both are the four-state rule
  being half-implemented in the most damaging direction: not "no error state",
  but "an error state that looks like data loss."
- **Bugs filed:** `BUG-20260822-layout-error-fabricated`,
  `BUG-20260822-dashboard-error-state`, `BUG-20260823-error-state-retry-delay`
- **Paper cuts:** the 7.7s skeleton before the designed error appeared — filed
  as its own minor rather than deferred, because the screen reads as frozen for
  those seconds.

### The auth lane (Nina) — one mailbox, two accounts

- **Ran:** iterations 19–26, 101–104
- **Findings:** email was compared as a raw string end to end. A phone keyboard
  auto-capitalising the first letter was enough to split one mailbox into two
  accounts, and then login picked between them by **heap order** — so the
  losing owner typed their own correct password and got
  `INVALIDCREDENTIALS`, permanently, with the winner able to flip after any
  unrelated write.
- **Bugs filed:** `BUG-20260823-email-case-splits-account`,
  `BUG-20260827-login-multi-row-heap-order`, `BUG-20260822-auth-unhandled-rejection`
- **Escalated:** `ESC-20260827-register-case-race` — closing the race needs a
  unique index, and the index will fail on existing data (`crafthub_dev` already
  holds six colliding mailboxes). Choosing which of two real accounts survives
  is a product decision.

### The mobile lane (Priya) — a search that gave no sign of having run

- **Ran:** iterations 54–60
- **Findings:** on a 390×844 phone, a successful "Search Top 50" produced a
  pixel-identical screen — results landed at `top=1069` in an 844px viewport,
  nothing scrolled, nothing moved focus, and the live region said nothing on
  success. Measured: 3 taps → 3× `POST /search`. Not a cosmetic finding; it is a
  request storm caused by absent feedback.
- **Bugs filed:** `BUG-20260823-mobile-search-no-feedback`

### Root causes, grouped

- **`disclosure-policy` (7)** — every one was the same shape: a *derived* form of
  a blocked term (URL slug, underscore join, cross-role attribution, tech-stack
  entry, tool-response label) escaping a literal comparison. The durable fix was
  making the read path call the *same detector function* as the write path, not
  making it produce the same answer on the example in the test.
- **`api-contract` (3)** — `public-posts-contract` (the api projection dropped
  `metadata`, the web schema required it), `mcp-overstates-redaction`,
  `resume-parse-uncapped` (a shared 100 000-char cap that was dead code).
- **`null-data` / four-state (3)** — `layout-error-fabricated`,
  `dashboard-error-state`, `error-state-retry-delay`.
- **`auth-permission` (3)** — `email-case-splits-account`,
  `login-multi-row-heap-order`, `agent-self-publish`.

- **`third-party` (2)** — dnd-kit's `defaultSensors` with no `coordinateGetter`;

## Decisions for a Human

Three items were escalated rather than fixed. Full write-ups in
`docs/qa/bugs/ESC-*.md`.

### One mailbox can still become two accounts (`ESC-20260827-register-case-race`, major)

- **What's broken:** two concurrent `POST /auth/register` for the same mailbox in
  different cases both return 201. Re-verified live at iteration 117 with a fresh
  pair.
- **Why not auto-fixed:** a check-then-insert race cannot be closed in
  application code; it needs `CREATE UNIQUE INDEX ... ON users (lower(email))`.
  That migration **will fail on existing data** — `crafthub_dev` already holds six
  colliding mailboxes and production may hold more. Deciding which of two *real*
  accounts survives is a product decision.
- **Options:** 1. Ship the index now and let the migration fail loudly →
  deploy blocked until someone picks winners under time pressure.
  2. Ship `BUG-20260827-login-multi-row-heap-order` only (done) → the lockout
  is gone, duplicates can still be created. 3. Audit, merge, backfill, then
  index concurrently → correct, but its own task.
- **Recommendation:** option 3, as its own task after the deploy. Tonight's fix
  already removed the sharp edge. The same index also restores an index for the
  login lookup, which the 08-23 fix turned into a sequential scan — worth doing
  soon for that reason alone.

### Every DELETE 400s on `content-type: application/json` with no body (`ESC-20260822-delete-empty-json-body`, minor)

- **What's broken:** `DELETE /links/:id` with a JSON content-type and no body
  returns 400 instead of 404/200. Re-reproduced at iteration 53.
- **Why not auto-fixed:** the fix is a **global request-parsing change**
  (`addContentTypeParser` for empty JSON bodies) touching the parse path of every
  POST/PUT/PATCH on the api, on deploy eve, to remove a 400 **no shipped client
  currently hits** — the web app's real delete journey passes, and `apps/mcp` has
  no delete tool at all.
- **Options:** 1. Global parser change now — riskier than the symptom.
  2. Per-route body-schema relaxation — narrower, more places to forget.
  3. Defer.
- **Recommendation:** defer. Do it as its own task with an HTTP test via
  `build-test-app.ts` + `server.inject`, and re-run the full api suite for parser
  regressions. The exposure is third-party agent authors, not shipped users.

### A two-word employer split across URL path segments still leaks (`ESC-20260827-disclosure-slash-gap`, minor)

- **What's broken:** `github.com/acme/corp` is not detected as naming "Acme Corp".
- **Why not auto-fixed:** unlike the underscore case, adding `/` to the separator
  set is a **widening**. The term "Data Science" would then match
  `site.com/data/science-fair`, and a new false positive is a 400 on a publish
  the night before a deploy.
- **Options:** 1. Widen now — accepts unknown false-positive rate.
  2. Widen with a measured corpus first. 3. Leave it.
- **Recommendation:** option 2. Needs a product call on false-positive tolerance
  plus a corpus of real `externalUrl` values to measure against.

## Learnings

- **The highest-yield question in review was not "is the fix correct?" but "does
  the fix call the same function as the path it has to agree with?"** Several
  proposed fixes passed their own authored test and would still have leaked on an
  input nobody wrote a test for. Reusing the existing detector, rather than
  writing a second predicate that happens to agree on the example, is what made
  the disclosure fixes durable.
- **An error state that renders plausible data is worse than no error state.**
  Two of the four-state findings were not "the error branch is missing" but "the
  error branch draws something that looks like the user's account, wiped." The
  four-state rule should be read as *four distinguishable states*, not four
  branches.
- **Absent feedback is a performance bug.** The mobile search finding was
  measurable as a 3× request multiplier, which is what moved it over the
  real-user-impact bar. Framing UI feedback gaps in request counts is what
  separates them from cosmetics.
- **Rejecting is the job too.** 15 of 41 triaged candidates (37%) were rejected —
  8 as below-bar, 5 as harness, 1 as a dev-server artifact, 1 as
  not-reproducible. Without that discipline the night would have churned
  cosmetics and shipped riskier diffs.
- **`npm run check-types` reporting FULL TURBO is not evidence.** Several
  iterations had to force `npx tsc --noEmit` inside the affected workspace to get
  a real answer. Worth knowing before trusting a cached green.
