## 0. Em poucas palavras

Hoje o repositório tem 11 skills e nenhuma cobre o dia a dia: commitar, abrir PR, pegar uma issue, planejar antes de implementar. Este plano cria seis fluxos, todos chamados por nome:

- `/commit-push-pr` — commita, roda o CodeRabbit, dá push, abre o PR no GitHub e atualiza a issue no Linear. Cada etapa é opcional e roda sozinha.
- `/bug-resolver` — lê a issue, **pergunta o contexto antes de investigar**, escreve um teste que falha, corrige a causa, e só então fecha o portão.
- `/linear-work` — lista suas issues do ciclo, mostra o card e decide o caminho.
- `/guardrails-repair` — quando `npm run guardrails` reprova, conserta a causa (nunca esconde o sinal).
- `/plan` e `/implement` — um único markdown em `docs/plans/`, com uma lista de verificação que serve de placar; um subagente audita antes da entrega.

**Antes de começar:** o Linear já é usado pelo time, mas ainda não está ligado a este repositório. O agente vai pedir a chave do time, o servidor MCP e se a integração com o GitHub está ligada antes de escrever qualquer constante (STOP-1).

## 3. Design decisions (do not re-litigate)

- **D1 — one shared reference**, `.agents/references/linear-github.md` **(new)**: GitHub org/repo derived at runtime from `git remote -v` (never hardcoded), base default, the `gh` command table, URL shapes, the Linear block filled **only from STOP-1 answers**, the `--all-default` convention and the `$ARGUMENTS` fallback (both written out in §10), the no-MCP fallback sentence, and the portable-git table. Six files cite it by repo-relative path; none repeats it.
- **D2 — `guardrails-repair` is its own skill**, scaled to what exists: one runner, no modes, no `--only`. Its failure table has one row per step name the runner prints. The coverage ratchet is **not** in that table (it is not a gate step, §2) — it appears as a note pointing at `npm run test:coverage --workspace=api`.
- **D3 — `commit-push-pr` is a menu of five independent steps** `commit review push pr linear`. `$ARGUMENTS` selects; none → status line + menu; a step whose precondition is missing is skipped with one line saying why. Preconditions and standalone paths: §10.1.
- **D4 — no `--no-verify`, ever**, with no sanctioned exception. `.husky/pre-push` already names the honest fallback: a human who uses it says so in the PR.
- **D5 — CodeRabbit: authenticate once** (preflight tree in §10.2) and **the local CLI and the GitHub PR bot are two products**. `coderabbit review --agent` runs on the developer's machine against the diff before the PR exists; the cloud bot reviews the PR afterwards _only if_ the repo is installed on app.coderabbit.ai — nothing here configures it (no `.coderabbit.yaml`), so the skill treats a bot review as possible, never waits for one, and never lets its absence pass as a review.
- **D6 — findings applied by judgment**: apply, or decline with a one-line reason; summary table; one follow-up commit (§10.2).
- **D7 — PR transport is `gh`, one path**: preflight `gh auth status`; `gh pr create --base <target> --title <t> --body-file <file>`; verify `gh pr view --json url,number`; already open (`gh pr list --head <branch>`) → `gh pr edit`. Add an MCP branch only if `.mcp.json` gains a GitHub server.
- **D8 — `bug-resolver` phase order** (nine phases, §10.5). No Jam MCP here: the investigation phase uses one if present, else asks the user to paste console output, the failing request and the exact steps — it never proceeds on an unstated reproduction.
- **D9 — new skill `linear-work`**, user-invoked. `disable-model-invocation: true` is Claude-Code-only and no skill in this repo has an `agents/openai.yaml`; in Codex and Kiro the description's "Invoked by name with `/linear-work`" clause is the only guard — say so in the skill.
- **D10 — `linear-work` routes by the issue's own label/type, read not asked**: bug → `bug-resolver` with the key as argument; anything else → `implement` · `plan` · Linear-only actions · nothing.
- **D11 — cross-platform** = `git`/`npm`/`npx`/`node`/`gh`/`coderabbit`/MCP names only, plus: `db-manage.sh` is **cited, not ported**, preferring its npm alias, with the Git Bash/WSL note where the bash form is unavoidable.
- **D12 — `--all-default`**, written out once in D1's reference (§10.3). It never skips the red test, the gate, or the `dod-auditor` run.
- **D13 — the skills open their own PR**: the executor uses the new `commit-push-pr` on this branch.
- **D14 — `plan` + `implement` are one markdown file, not a pipeline.** `/plan` interviews (format in §10.6), writes `docs/plans/YYYY-MM-DD-<slug>.md` from the six-section template (§10.6), stops. `/implement <path>` starts fresh, reads only the plan and the files it names, and uses the plan's checkboxes as its progress ledger — conversation memory does not survive compaction. Separate sessions are the default; `--same-session` exists and prints a one-line context warning. DoD splits **Automated** (a command) from **Manual** (a route a human opens).
- **D15 — two read-only subagents** under `.agents/agents/` **(new)**, symlinked to `.claude/agents/<name>.md`: `dod-auditor` (contract in §10.8, including the discrimination check and the two-table output) and `plan-reviewer` (same read-only shape, run before the user approves a plan). Frontmatter write-blocked: `tools: Read, Glob, Grep, Bash` (omitting `tools` inherits Edit/Write), `model: inherit`. Kiro has no subagent concept — document that, do not invent a symlink.
- **D16 — minimal harness structure.** Add `.agents/agents/` and `.agents/references/` beside `.agents/skills/`; keep the flat root `AGENTS.md` plus a **≤15-line router section**. **Not doing, deliberately:** no `.agents/rules/` layer (nested `AGENTS.md` is the only path-scoping all four tools share, per `docs/harness/agent-harness.md:61`, and three nested files already cover api/web/schemas); no port of a multi-mode guardrails runner (the single affected-scoped script here is the same idea, already working); no twelve-laws split ("Non-negotiables" already is that list).
- **D17 — the `implement` proof pack is three sensors with an applicability rule.** (1) The changed workspace's vitest run — **always**. (2) An **API-level sensor**: a `*.e2e.test.ts` against the real Fastify app with `bash db-manage.sh start` up, per `apps/api/AGENTS.md`. (3) A **DB check through the `postgres` MCP server**: read-only, local dev DB, by a correlation id you control — `AGENTS.md` already forbids "it returned 201" as evidence; `psql` is not assumed installed. **Sensors 2 and 3 apply only when the change touches `apps/api` or the database; otherwise the report names them "not applicable — no API or DB surface changed".** Anything user-visible adds `visual-check`; a harness-only change adds `npm run harness:check` instead.

## 5. Specifications

**5.1 `.agents/references/linear-github.md`.** Sections: **GitHub** — org/repo resolved at runtime from `git remote -v`; base default `main` (the only branch CI gates); the `gh` table (`auth status`, `pr create --base --title --body-file`, `pr view --json url,number`, `pr edit`, `pr list --head <branch>`); PR/branch/issue URL shapes. **Linear** — team key, workspace, workflow **state names read from the API/MCP, never hardcoded** (a Linear team defines its own states; there is no Jira-style fixed transition id), label taxonomy, issue-key regex, branch naming = Linear's own "copy git branch name" `<username>/<key>-<slug>`. **PR ↔ Linear linking** — with the Linear GitHub integration on, `Closes LIN-123` in the PR body links and transitions the issue; off, the `linear` step comments instead (STOP-1c decides). Then **`--all-default`** (§10.3), the **no-MCP fallback** sentence, the **`$ARGUMENTS` fallback** (§10.4), and the **portable git table** (`git branch --show-current`; `git status --porcelain`; upstream via `git rev-parse --abbrev-ref --symbolic-full-name "@{u}"` **before** `git log --oneline "@{u}..HEAD"`).

**5.2 `guardrails-repair`.** Body: (1) read the failure, name the failing step. (2) The loop, max 3 rounds, then escalate with the diagnosis. (3) Step → meaning → real fix table, **one row per name the runner prints** — read them out of `scripts/guardrails/pre-push.mjs:490-510`, do not invent or import a list. A separate short list covers what runs _outside_ the runner: CI's `LINT_ERROR_BASELINE` job, and a note that the api coverage ratchet is enforced by `npm run test:coverage --workspace=api` and CI, never by the gate. (4) Forbidden repairs, one line each citing `no-workarounds`: `any`, a widened zod schema, `eslint-disable`, `.skip`, `--no-verify`, a lowered coverage threshold, a raised lint baseline. (5) Environmental failures that look like code failures: stale `node_modules` or an unbuilt `@repo/schemas` after a rebase → `npm ci && npm run build:schemas` **before** touching code; docker down → `bash db-manage.sh start` (Git Bash/WSL on Windows) and the gate's own skip notice explains itself; no `OPENAI_API_KEY` → three named files skip by design; **ports 3333/5173 owned by another project** → the `weg/retro-doc` incident, probe the title/route before believing any browser, e2e or API result. (6) Report: what failed, the cause, what changed, the green re-run line.

**5.3 `commit-push-pr`.** Five steps per D3 and §10.1, each with its own precondition sentence and a standalone path. `argument-hint: "[commit] [review] [push] [pr] [linear] [--issue <LIN-key>] [--base <branch>] [--all-default]"`. **Status line first** (printed before any menu, no questions asked to build it): branch · issue key (`--issue` > the caller's key > regex on the branch > none) · dirty file count · upstream present, then unpushed commits · open PR for this branch · which of `gh` / `coderabbit` / the Linear MCP answer. Then the §10.3 `--all-default` block verbatim and the §10.4 argument fallback. Transport is `gh` only (D7). The `pr` step writes `--body-file` from `references/pr-template.md` (never an inline `\n`-escaped string) and puts `Closes <LIN-key>` in the body when STOP-1c says the integration is on. The `linear` step comments the PR link + branch, then moves state by **reading the team's workflow states first** and choosing the one matching "in review" / "code review"; there is **no "AI adoption" field** — Linear has no such built-in, so the skill sets a custom field only if STOP-1d reports one, and otherwise says nothing. `references/coderabbit.md` contents, in order: the §10.2 preflight tree; the two auth commands with bash and PowerShell variants of the env-var form; "never print or commit the key"; the CLI-vs-cloud-bot paragraph (D5); `coderabbit review findings` to re-read the last run; the apply/decline rule and the summary-table shape.

**5.4 `bug-resolver`.** Nine phases exactly as §10.5. The ticket source is Linear (`linear-work` may hand the key over) or a manual description. No Jam MCP: the investigation phase opens with the "use it if present, otherwise ask for pasted evidence" rule. The red test is vitest (`npm run test --workspace=api|web -- <path>`) and `references/red-test.md` carries where a test belongs — use-case test vs an e2e built on `apps/api/src/infra/http/test-support/build-test-app.ts` vs a `@repo/schemas` contract assertion vs RTL vs the visual runner — citing `testing-boss` and `apps/api/AGENTS.md` rather than restating them. The gate is `npm run guardrails`. Root cause is recorded in the Linear comment (no custom field). Visible bugs run `visual-check`. The hand-off menu ends in `commit-push-pr`.

**5.5 `linear-work`** (conditional on STOP-1). Default list = the developer's issues in the active cycle, not Done, via the Linear MCP (`assignee = me`, `cycle = current` — **write the actual filter from the server's own tool listing, per STOP-1e, not from this sentence**); an argument may be a key, a label filter or a raw filter. `references/issue-card.md` renders title, state, priority, cycle, project/parent, labels, description, every comment, attachments, and links classified (GitHub PR / Figma / doc / other). Routes per D10. The implement route _delegates_ to the `implement` skill instead of inlining an implementation flow.

**5.6 `plan` and `implement`.** `plan`: interview per §10.6 → write the file from `references/plan-template.md` (the six sections of §10.6) → offer `plan-reviewer` → stop, printing the path. Auto-size: a ≤3-file change gets a 20-line plan. Rules are **cited, never inlined** (`AGENTS.md` non-negotiables, `apps/<app>/AGENTS.md`, `DESIGN.md`). It states when to use the other lane: a multi-screen feature with a design and acceptance criteria goes to `spec-writer`/`spec-implement`; everything smaller goes here. `implement`: read the plan and only the files it names → task by task, checking boxes in the file as the ledger → **red-first mandatory for a bug, recommended for a feature**, and either way the report carries the RED command, its failing output, why that failure was expected, then GREEN (§10.7) → remaining coverage (edge cases, error branches) in the same task; if coverage moved up, measure with `npm run test:coverage --workspace=api` and raise the `apps/api/vitest.config.ts` floor in the same commit → the D17 proof pack, each sensor reported as run or **not applicable** → `npm run guardrails` → dispatch `dod-auditor` (never optional, never skipped by `--all-default`) → ≤3 fix rounds → hand off to `commit-push-pr`. Banned outright: mirror assertions, mock-existence assertions, change detectors, partial mocks missing fields the code reads. Pitfall paragraph: before trusting any browser, e2e or API probe, confirm 3333/5173 belong to _this_ app (§5.2).

## 10. Skill shapes (condensed)

Everything the specifications above reuse, written out here so no file outside this repo is needed.

**10.1 `commit-push-pr` steps.** Each step detects its own precondition, runs standalone in any subset and any order, and prints one line when it skips.

- `commit` — precondition: `git status --porcelain` non-empty. Stage only files related to the change and name what was left out and why; one or more Conventional commits with a pt-BR description. **No commit-time hook exists in this repo**, so the step runs `npm run guardrails` first; red → `guardrails-repair`, never `--no-verify`. A caller skill's summary becomes the message body.
- `review` — precondition: `coderabbit` on PATH and authenticated (§10.2). Nothing to review → skip.
- `push` — precondition: unpushed commits (check the upstream _first_: no upstream → `git push -u`, and skip the log check). The husky `pre-push` gate runs here; red → `guardrails-repair`. A rejected non-fast-forward is explained, `git pull --rebase` proposed, and the user asked.
- `pr` — precondition: the branch is pushed. Target from `--base`, the caller, else ask with the `main` default. Already open (`gh pr list --head <branch>`) → `gh pr edit` instead of create. Print the clickable PR URL.
- `linear` — precondition: an issue key **and** a Linear MCP that answers. Sub-menu (comment · state · anything STOP-1d added), defaults = all. No key or no MCP → one line saying the step was skipped, plus the list of actions for the user to do by hand.

**10.2 CodeRabbit preflight tree and triage.** Run `coderabbit auth status`. Signed in → proceed. Not signed in and `CODERABBIT_API_KEY` is in the environment → `coderabbit auth login --api-key` reading the variable, **never echoing it**. Not signed in and no variable → print the one-time login command for the user's OS and **wait**; skipping a step the user selected is never the agent's call. Then: on a clean tree after `commit`, `coderabbit review --agent --committed --base <target>`; on a dirty tree, `--uncommitted` instead. Triage every finding by judgment — apply it (root-cause fix, gate stays green) or decline it with a one-line reason; show a summary table of applied ✅ / declined ⏭️ with the reason column; a declined finding is never hidden. Anything applied lands in one follow-up commit. `coderabbit doctor` is the one-shot diagnosis, run from the tool's own terminal.

**10.3 `--all-default`** (5 lines, stated once in the reference, cited by every skill). Passed as an argument = the user has already confirmed; typed mid-flow = ask once, then stop asking. After that: take every default, or option 1 where there is no default, and narrate each choice as it is made. It **never** skips the red test, the gate, or the `dod-auditor` run.

**10.4 Argument fallback.** Where `$ARGUMENTS` is not substituted (Kiro, Cursor, Codex, Copilot), the words the user typed after the skill name are the arguments; none → show the menu.

**10.5 `bug-resolver` phases.** 1 **Select** — a key as argument (typed, or handed over by `linear-work`) skips only the search; else search, or "describe manually". This phase owns the base-branch question and the branch creation, whoever invoked the skill. 2 **Read the issue** — description, every comment, attachments, linked issues and links, collected _as links only_. 3 **Overview + the three optional questions in one message** — what the user already knows about the cause / which files they suspect / which cases must be covered; "answer in one text, by number, or say skip". 4 **Investigate** — _only now_: Jam MCP if present else pasted evidence, code search from the issue's terms, reproduction in the browser via `visual-check` when visible. 5 **Plan + approval** — cause, strategy, files, tests; "approved? 1 yes / 2 adjust". 6 **Red test** — watch it fail for the right reason. 7 **Fix** at the root cause, `no-workarounds` loaded. 8 **Gate + record** — `npm run guardrails`, then the root-cause comment on the issue. 9 **Hand-off menu** — `commit-push-pr` (all steps) · commit only and go to the next bug · stop.

**10.6 Plan file and interview.** The file has exactly six sections: **Goal** (one sentence) · **Current state** (3-8 bullets, each with a `file:line`) · **Not doing** · **Tasks** (each: files to create/modify/test · steps · proof) · **Definition of Done** split `### Automated` (each box names the command) and `### Manual` (each box names the route and how to reach it) · **Open questions / assumptions** (`[ASSUMPTION]` lines the user can veto). No placeholders: never "TBD", never "add appropriate error handling". Interview: **at most 5 questions, one per turn**, each as a full interrogative sentence + one "why it matters" line + 2-5 mutually exclusive options + `**Recommended:** <option> — <reason>`, and "reply with the option, or say yes to take the recommendation". Stop when the critical ambiguity is gone, the user says done, or 5 have been asked; everything still unknown becomes an `[ASSUMPTION]` line, never a sixth question. Under `--all-default` the questions are shown with their recommended answers already taken, not waited on.

**10.7 Implementer → auditor hand-off.** Under 15 lines: **status** one of `DONE` · `DONE_WITH_CONCERNS` · `BLOCKED` · `NEEDS_CONTEXT`; what changed, by file; **TDD evidence** — the RED command, its failing output, and why that failure was the expected one, then the GREEN command and its passing output; the D17 proof pack with each sensor marked run or _not applicable_; anything the implementer could not verify. Warnings and noise in the reported test output are findings, not decoration.

**10.8 `dod-auditor` contract.** Informed but adversarial: it receives the plan's DoD, the diff (pre-computed to a file), and the implementer's report **explicitly labelled unverified claims**. Two stages in one pass — (1) DoD compliance, per box met / missing / extra / misunderstood; (2) code quality: error handling, duplication, tests that assert real behaviour. **Evidence or zero**: every verdict cites `file:line` or the command it ran; an unsupported box counts as not met. It is read-only, spawns no subagents, and does not re-run the whole suite. **Discrimination check**: mutate behaviour in 1-2 of the files the DoD actually turns on — in a temp worktree or file copies, **never `git stash`** — and confirm a test dies for each; a surviving mutation is a finding. Output is two tables: per-box verdicts, then findings as id · severity (blocking / should / nit) · `file:line` · what is wrong · the smallest fix, ending with the count per severity. Loop bounded to 3 rounds, then escalate to the human with the open findings listed.
